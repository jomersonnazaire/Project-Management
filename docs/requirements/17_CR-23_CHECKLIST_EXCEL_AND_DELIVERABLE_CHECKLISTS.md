# Part A — Checklist Excel (Locked reuse, Lean, 2026-11-11 ~8:55 AM SGT; one file on the Checklist screen, Jomerson then Lean, ~9:08 AM SGT)

## A1. Scope

**In scope (Locked):** there is **one Excel import and download**, on the project **Checklist** tab. The project's PM and Admins can **download a checklist template**, **download the current checklist** as the same workbook, and **upload / update via Excel**, with a **preview**, **row errors**, and the **same limits** as the CR-22 Timeline import (5 MB, 2,000 rows, preview-then-commit, hidden Task ID, hidden `_meta` sheet). This **replaces** the Timeline Excel import: the Timeline Excel menu, template and toolbar Excel actions are **removed** (Q-152 and Q-163 re-closed by **Jomerson**, 2026-11-11 ~9:08 AM SGT; **Lean**, same window: the download also moves, and there is **one format** for upload and download). The Checklist file carries the **CR-22 Timeline columns** (phases, dates, Depends on, and the rest of CR-22 §B4) **plus a Deliverables column**. The Timeline **view** still shows whatever the Checklist file sets (dates, phases, dependencies, baselines). The CR-22 Timeline **import** FRs (FR-TL-14 to 22, 25, 26 and related FR-TL-19 / FR-TL-32) are **superseded** and apply on the Checklist screen; FR-CLX-* restates them and points back to those IDs where the rule is unchanged. The file is imported **into the open project**. Phase matching and new-phase rules reuse FR-TL-20 unless Q-159 changes them. Owner-not-on-team reuses FR-TL-21 unless Q-151 changes it; **Lean (2026-11-11 ~9:03 AM SGT): do not build owner auto-add yet.** Deliverable items **round-trip** through the Checklist file's Deliverables column (Q-158 closed: one item per line, `[x] ` on done items, re-upload replaces the list, blank cell clears, preview lists cleared and unticked items).

**Out of locked scope until questions close:** creating a **new project** from the file (Q-150); auto-adding owners named in the file to the team (Q-151 — do not build yet).

**Not in this part:** the deliverable checklist UI (Part B), except that the Checklist file carries items in the Deliverables column.

## A3. User stories

- **US-75** As a project's PM (or an Admin), I want to download a checklist template, download the current checklist, and import an Excel file with a preview of errors, so I can add or update activities (including dates, phases, dependencies and deliverable items) in a spreadsheet without breaking the project. This is the only Excel import; the Timeline tab has no Excel menu.
- **US-76** As a project's PM, I want a new phase name in the file to be added to this project when I'm allowed to add phases, so I don't have to create every phase by hand first. *(What "Add Phase and Project" means beyond this is Q-150.)*

## A4. Acceptance criteria

- **AC-75.1 (API/UI)** A planner on the project sees Download template, Download checklist and Import on the Checklist tab, and can complete a preview-then-commit of a valid file. A Member or Viewer does not see the buttons; `GET` template/export and `POST` preview/commit each return 403. A PM who is not on the project gets 404. The Timeline tab has **no** Excel buttons or menu; its former template, export and import routes are gone (or return 404). (FR-PRJ-42, FR-CLX-01, Q-152)
- **AC-75.2 (API)** The blank **Checklist** template has the CR-22 Timeline columns **plus a Deliverables column**, an Instructions sheet, a hidden Task ID column (empty) and a `_meta` sheet without a project id; every row of a filled-in copy imports as a new task on the open project. There is **no** separate Timeline template. Downloading the current checklist uses this **same format**. (FR-CLX-02, FR-CLX-04, A-54, Q-163)
- **AC-75.3 (API)** Exporting the current checklist and re-importing the file unchanged shows every row as Unchanged and saves nothing. After a task is deleted in the app (numbers shift, CR-20), re-importing an earlier export updates the right tasks by Task ID and never deletes a task that is missing from the file. (FR-CLX-02, FR-CLX-04)
- **AC-75.4 (API/UI)** Each file error and row error uses the CR-22 §B5 copy where the rule is the same; nothing is saved before confirm; any row error blocks the whole commit; the preview lists fields that a blank cell will clear, and for Deliverables it lists **cleared and unticked** items row by row. (FR-CLX-02, FR-CLX-04, Q-158)
- **AC-75.5 (API)** A file larger than 5 MB, or with more than 2,000 data rows, is refused with the CR-22 / UIE Q24 messages and nothing is saved. Rate limits follow NFR-55 (one engine, one set of limits; Q-164 superseded). (FR-CLX-02, NFR-55)
- **AC-75.6 (API)** Import on a Completed project returns 422 `PROJECT_COMPLETED`; on an archived project, 409 `PROJECT_ARCHIVED`; on a Cancelled project, refused as not importable, same as Timeline import (FR-CLX-03, FR-TL-20 / Q-141, Q-155). (FR-CLX-03)
- **AC-75.7 (API/UI)** On a Planning project, a new phase name "Go-live" in the file is added at the end of the phase list with a preview warning, and tasks in that row link to it by `phaseId`. On an Active project, the same file is a row error for the project's PM and succeeds for an Admin. (FR-CLX-05, Q-159)
- **AC-75.8 (API/UI)** A row whose Owner is `owner@xceler8.example` when that user is active but not on the project is a row error with the FR-TL-21 message, and the user is not added to `memberIds`. Owner auto-add is not built (Q-151 open; Lean: do not build it yet). (FR-CLX-06)
- **AC-75.9 (UI)** At 390, opening Import shows "Open this on a larger screen to make changes" and does not show the preview table. (FR-CLX-08)
- **AC-75.10 (API/UI)** A task has two items, "Workshop notes" (open) and "Signed-off test script" (done). Export writes them in the Checklist Deliverables cell as two lines, the done item starting with `[x] ` (for example `Workshop notes` on one line and `[x] Signed-off test script` on the next). Re-importing that file unchanged shows the row as Unchanged. Re-importing a file whose Deliverables cell has only `Workshop notes` **replaces** the list with that one open item: the preview lists "Signed-off test script" as cleared, and after confirm the done item is gone. Re-importing a file whose cell has `Signed-off test script` without `[x] ` (and omits the other item) lists "Signed-off test script" as **unticked** and "Workshop notes" as cleared; after confirm the list is that one open item. A blank Deliverables cell lists the items as cleared in the preview and, after confirm, leaves the task with no items. (FR-CLX-04, Q-158)

## A5. Edge cases

- **EC-206** Two planners preview overlapping files for the same project: commit handling follows CR-19 / CR-22 (409 `PREVIEW_STALE` or 429 `IMPORT_BUSY`); nothing is half-saved. (FR-CLX-02, NFR-55)
- **EC-207** A file whose `_meta` project id is another project, or a made-up id, is refused (FR-TL-26); a Task ID from another project is a row error. Nothing in the open project changes, and no new project is created (Q-150).

# Part B — Deliverable checklists (Locked direction, Lean, 2026-11-11 ~8:55 AM SGT; who may add and tick, Jomerson then Lean, ~9:08 AM SGT)

## B1. Scope

**In scope (Locked):** each task's **Deliverable** becomes a **checklist**: users can **create a list of records** as checkboxes; when an item is completed it is **checked** and shown with a **line through** the text. **Who may add and tick (Locked, Jomerson then Lean, 2026-11-11 ~9:08 AM SGT):** only the task's **owner**, the project's **PM**, and **Admins** can **add and tick** deliverable items. **Admins** keep their usual **everywhere** access. **Everyone else**, including **assignees**, other members and **Viewers**, sees the list **read-only**. This overrides Lean's earlier FR-TSK-14 rule (Q-153 re-closed by Jomerson; Q-166 closed by Lean; adding confirmed as the same rule — Lean: "add or tick"). Existing `deliverable` **plain text on both Task and Template** is migrated to checklist items; templates used to launch new projects carry those items **unticked** (FR-DLV-04, Deven's note on Q-160).

**Limits, audit, status independence and migration (Locked, Lean, 2026-11-11 ~9:06 AM SGT, as Rich suggested):** 50 items per task, 200 characters on new items, with untick / edit text / delete allowed for owner, PM and Admin, including on a done item (Q-156); each add, tick, untick, edit, reorder and delete is audited (Q-157); ticking items does not change task status (Q-162); migrated and template-copied text is not truncated (Q-160).

## B2. Data model

Storage (Deven may adjust names, not the fields): a `deliverableItems` array of subdocuments on **`Task`** (`apps/api/src/models/Task.ts`) **and** on each **template activity** (`apps/api/src/models/Template.ts`), not a separate collection, so a task or activity and its items stay in one write. The existing task `version` can guard concurrency on tasks (EC-18).

| Field | Type | Rule |
|---|---|---|
| `_id` | ObjectId | Stable item id, used in the API. The Checklist file's Deliverables column identifies items by text and `[x] ` mark (Q-158), not by this id. |
| `text` | String, required, trimmed | Max **200** characters on **new** items (Q-156). Migrated or template-copied text may be longer and is not truncated (Q-160). Reject blank text on new items. |
| `done` | Boolean, default `false` | Ticked = `true`. Template items, and items copied onto a new project, are **unticked**. |
| `doneBy` | ObjectId ref User, or null | Set when ticked; cleared when unticked. Null on template items and on migration. |
| `doneAt` | Date, or null | Set when ticked (server clock); cleared when unticked. Null on template items and on migration. |
| `order` | Number | Display order, 1…n in the list; reordering changes only this, like FR-PRJ-16 |
| `createdBy` | ObjectId ref User, or null | Null is allowed for migrated items (no original author) |
| `createdAt` | Date | Set on create or at migration |

Index: none beyond the parent task or template. **Caps (Q-156 closed, Lean, 2026-11-11 ~9:06 AM SGT):** **50 items** per task or activity; text **200** characters on new items. Zod in `@xc8/shared`, alongside `createTaskSchema`.

Today `Task.deliverable` and template activity `deliverable` are both **plain text** (max 500). Both are **superseded** by `deliverableItems` after the one-time migration (FR-TSK-38, FR-DLV-04). After migration those string fields are no longer accepted on create or update.

## B3. Functional requirements

- **FR-DLV-01 (Must, Locked)** A task's Deliverable is a **list of checklist items** (FR-DLV data model above), not a single text field. The task form and the task panel show this list in place of the Deliverable text box. A template activity holds the same kind of list, all items unticked.

- **FR-TSK-38 (Must)** Amends FR-TSK-01, FR-TPL-03, FR-PRJ-02 and the task form / panel. The single `deliverable` string is removed from write APIs after migration. GET may omit it or keep it read-only as a join of item texts for old clients during one release; new work must use `deliverableItems`. When a plan is generated or a template is applied, the template activity's **checklist items** are copied onto the new task **unticked** (`done: false`, `doneBy` / `doneAt` null), in the same order (FR-DLV-04, Deven's note on Q-160).

- **FR-DLV-02 (Must, Locked, Jomerson then Lean, 2026-11-11 ~9:08 AM SGT)** The task's **owner**, the project's **PM**, and **Admins** may **add** an item by entering text. A new item starts with `done: false` and no `doneBy` / `doneAt`. **Admins** keep their usual **everywhere** access (they may add on any project's tasks, as they can today for plan-level edits). **Everyone else**, including **assignees**, other Members, and **Viewers**, sees the list **read-only** and cannot add. This **overrides** Lean's earlier call that anyone who can edit the task under FR-TSK-14 (including assignees) could add and tick, and it **closes** the add-items assumption: adding uses the **same rule** as ticking (Lean: "add or tick"). Client portal users are out of v1. This closes Q-153, Q-161, Q-154 and Q-166. There is no "any project member may add" rule, and being an assignee is not enough.

- **FR-DLV-03 (Must, Locked, Jomerson then Lean, 2026-11-11 ~9:08 AM SGT)** When an item is **ticked**, the API sets `done: true`, `doneBy` to the current user and `doneAt` to now, and the UI shows the item **checked** with a **line through the text**. Strikethrough is **not** the only done cue (NFR-57): the checkbox is in the checked state, and a non-colour, non-strikethrough cue is required (for example a visible "Done" label and `aria-checked="true"`). **Who may tick** is the same set as who may add (FR-DLV-02): the task's **owner**, the project's **PM**, and **Admins**. Everyone else is read-only, including assignees. **Untick, edit text, delete and reorder are allowed** (Q-156 closed, Lean, 2026-11-11 ~9:06 AM SGT), including on a done item, and are limited to those same people. Unticking clears `done`, `doneBy` and `doneAt`.

- **FR-DLV-04 (Must)** **Migration of existing text (Task and Template).** Today `deliverable` is **plain text** on both **Task** and **Template** activities (Deven, recorded on Q-160). The one-time migration **converts both**:
  - Every **task** whose `deliverable` string is non-empty and which has no `deliverableItems` yet gains **one first item**: `text` = the trimmed string, `done` = false, `order` = 1, `createdBy` = null, `createdAt` = the migration time, `doneBy` / `doneAt` = null.
  - Every **template activity** is converted the same way into `deliverableItems` on that activity, all **unticked**.
  - Empty or null strings leave the list empty. The migration is one-time, safe to re-run (a task or activity that already has items is left as is), has a dry-run that lists the changes, reports how many tasks and template activities it changed, and runs on live only after Jomerson's OK (same pattern as FR-TSK-33). After a record has been migrated, create and update **reject** the old `deliverable` field (422).
  - **Templates used to launch new projects** (generate plan or apply template) **carry the checklist items, unticked**, onto the new tasks (FR-TSK-38).
  - **Over-cap text (Q-160 closed, Lean, 2026-11-11 ~9:06 AM SGT, as Rich suggested):** do **not** silently truncate a migrated or template-copied string; keep the full original text on that item even if it is longer than the new cap, and apply the cap only to items created after the release.

- **FR-DLV-05 (Must)** Suggested API (Deven may rename paths; behaviour stays). All of these need the FR-DLV-02 permission (the caller is the task's owner, the project's PM, or an Admin), and are refused on Completed, Cancelled and archived projects (FR-DLV-06):
  - Task DTOs include `deliverableItems: [{ id, text, done, doneBy: { id, name } \| null, doneAt, order, createdBy: { id, name } \| null, createdAt }]`. Template DTOs include the same list (all `done: false`).
  - `POST /tasks/:id/deliverable-items` body `{ text }` → 201 and the new item (add).
  - `PATCH /tasks/:id/deliverable-items/:itemId` body `{ text? }` (edit text, if permitted) and/or `{ done: true \| false }` (tick / untick).
  - `POST /tasks/:id/deliverable-items/reorder` body `{ itemIds }` (display order only).
  - `DELETE /tasks/:id/deliverable-items/:itemId`.
  Concurrent edits follow the task `version` (EC-18): a stale write is 409. A missing item is 404. A caller who cannot add or tick gets 403.

- **FR-DLV-06 (Must, Locked, Lean, 2026-11-11 ~9:06 AM SGT)** **Completed, Cancelled and archived projects are read-only** for deliverable items (Q-155). Add, edit text, tick, untick, reorder and delete are refused: Completed → 422 `PROJECT_COMPLETED` ("This project is completed, so its plan is read-only. Reopen the project to change tasks."); archived → 409 `PROJECT_ARCHIVED` ("This project is archived. Restore it before making changes."); Cancelled is refused the same way as Timeline import (FR-TL-20 / Q-141). The list remains visible to anyone who can view the task.

- **FR-DLV-07 (Must, Locked, Lean, 2026-11-11 ~9:06 AM SGT)** Each add, text edit, tick, untick, reorder and delete is written to the audit log on the task (FR-AUD-01), with actions `deliverable_item_added`, `deliverable_item_updated`, `deliverable_item_ticked`, `deliverable_item_unticked`, `deliverable_items_reordered`, `deliverable_item_deleted`, and the item id plus old/new `text` or `done`. **Q-157 closed:** this audit is required.

- **FR-DLV-08 (Must)** **UI and accessibility.** The list is on the task panel and on the task form, in the Deliverable place. Add is a text field plus an Add control, shown only to users who may add (FR-DLV-02). Each row is a checkbox and the item text; a done row is checked and struck through, plus the second cue in FR-DLV-03. Checkboxes are disabled for read-only viewers of the list. At **390**, the checkbox, Add, and any row action (edit, delete) have a **44px** tap target. Empty state: "No deliverable items yet", with Add shown only to users who may add. A short summary on the Checklist row (for example "2/5") is left to UIE and is not required to ship the list. Colour is not the only done cue (NFR-57).

- **FR-DLV-09 (Must, Locked, Lean, 2026-11-11 ~9:06 AM SGT)** Ticking items does **not** change the task's **status**, including when every item is ticked (Q-162). Completing the task still follows FR-TSK-04 and FR-TSK-05 (predecessors, For review / approval). The list and the status stay independent.
